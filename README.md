# Santai Badminton Club — version 1.0

A responsive, working club portal prepared for **GitHub Pages + Firebase Authentication + Cloud Firestore**, editable in free Visual Studio Code. No website build step is required. JavaScript modules run in the browser; Firebase security rules enforce access at the database.

**Delivery status:** source implementation and demonstration are provided. No GitHub repository or live Firebase project has been connected. The demo uses fictional member records in memory; reloading clears demo changes. Real credentials, delivery of verification emails, bank QR and deployment must be tested with your project before inviting the club.

Start with **START-HERE.html**, which opens as a readable guide in your browser.

## Included

- Owner, committee and member access. Committee finance and activity permissions are separate and expire at the Malaysia end-of-day selected by the owner.
- Email/password sign-in, email verification, password reset and owner approval of registrations. Passwords are handled by Firebase Auth, never stored in Firestore or GitHub.
- Full membership RM80/month. Owner records committee-approved percentage discounts. For example 10% = RM72, 20% = RM64, 30% = RM56, 50% = RM40.
- Monthly fees generated by a committee action; deterministic IDs make re-running safe. Existing issued fees are not repriced when discounts change.
- Ad hoc membership RM15 per recorded activity attendance; duplicate attendance is rejected. Full members pay no extra attendance charge.
- Partial payments, payment reporting by members, committee verification, personal payment history and printable acknowledgements.
- Club bank details and a genuine bank-supplied QR image. QR upload is restricted to raster PNG/JPEG/WebP and 150 KB, stored as a small Firestore settings field. No Firebase Storage is used.
- Paid expenses by category, monthly cash summaries, income/expense chart and issued-fee balances.
- Owner reversal of incorrect payments/expenses, with the original record retained and a reason. Reversal restates the original month; a payment reversal reopens that amount of the fee. Approved fee waivers reduce unpaid charges without adding cash income.
- Club sessions, courts, planned capacity, venue costs, internal tournaments, friendlies, RSVP interest, attendance, notes, draws and scores as committee-entered text.
- CSV export of personal payments and club monthly totals, owner JSON backup, club announcement and an application activity log.

## Access matrix

| Capability | Owner | Finance committee | Activity committee | Member |
|---|---|---|---|---|
| Own fees and payment submissions | Yes | Yes | Yes | Yes |
| Aggregate club monthly totals | Yes | Yes | Yes | Yes |
| Schedule and own RSVP | Yes | Yes | Yes | Yes |
| Other members' fee records | Yes | Yes | No | No |
| Record attendance, fees, verified payments, expenses, waivers | Yes | Yes | No | No |
| Edit schedule, fixtures and results | Yes | Only with activities permission | Yes | No |
| Approve members, discounts, roles and terms | Yes | No | No | No |
| Change bank/QR, reverse financial entries, export full backup | Yes | No | No | No |

You may give one committee member both permissions. An expired committee member retains ordinary member access while their membership remains active. Suspension blocks club data access.

## Free hosting and database setup

1. Extract the ZIP. Open the **santai-badminton-club** folder in VS Code.
2. For the easiest preview, double-click **DEMO.html**. This standalone demonstration needs no installation and cannot connect to live records. To preview/edit the actual website, use a local HTTP server (VS Code **Live Server** extension is suitable) and open `docs/index.html` with Live Server. Do not double-click `docs/index.html`: its ES modules need HTTP. The standalone START-HERE guide can also be double-clicked.
3. Choose **Explore demonstration**. Use the role selector to inspect owner, committee and member screens. Sample changes never go into Firebase.
4. Create or choose a Firebase project in [Firebase Console](https://console.firebase.google.com/). Keep the **Spark** plan. Analytics is optional and not used here.
5. Add a **Web app** in Project settings. Copy the public `apiKey`, `authDomain`, `projectId`, and `appId` into `docs/firebase-config.js`. Preserve quotation marks and commas. These identify the public web app; authorization comes from Auth and Firestore rules. Never add service-account or Admin SDK credentials to the site.
6. Enable **Authentication → Sign-in method → Email/Password**. Enable only email/password (not email-link sign-in). Set the password minimum to at least 10 characters. Keep email enumeration protection enabled. Configure the support/sender name to Santai Badminton Club where the console permits it.
7. Create **Cloud Firestore → Standard edition → default database**, initially in **production mode**. Choose the appropriate location near your users (e.g. Singapore if offered). Replace the Rules tab contents with the entire `firestore.rules` file and publish. Do not use public test-mode rules. No composite indexes are required.
8. In Authentication settings, add your final Pages hostname (e.g. `yourusername.github.io`) under **Authorized domains**. Add `localhost` if previewing live sign-in locally; it may not be added automatically on newer projects. Do not include `https://` or a repository path in the domain entry.
9. Create a **public** GitHub repository such as `santai-badminton-club`, or use an existing one after reviewing its contents. For the free Pages option, the source repository is public. The files in `docs/` are website assets; private member data stays in Firestore.
10. Upload/commit the project files using VS Code Source Control or GitHub's Add file → Upload files. Preserve the `docs` folder. Do not upload node_modules, backup exports, bank statements or member spreadsheets. The ZIP includes `.gitignore` to help prevent accidental commits of backups and credentials.
11. GitHub repository **Settings → Pages → Build and deployment → Deploy from a branch → main → /docs → Save**. If your branch has a different name, choose that branch. Wait for GitHub to display the Pages URL. Use the link GitHub provides, normally `https://YOUR-USERNAME.github.io/santai-badminton-club/`.
12. Open that URL, create **your own owner account**, and verify your email. Initially it is a pending ordinary member; this is intentional.
13. Bootstrap the first owner **in your Firebase console**: find your UID in Authentication → Users. In Firestore → `members` → document with that exact UID, change only `role` (string) to `owner`, `status` (string) to `active`, and `approvedBy` (string) to your UID. Keep the remaining fields created by registration. Sign out and sign back in. Never change rules to allow self-promotion.
14. Open Settings in the club portal. Add your bank name, account holder, account number and real bank-generated QR. Set the reconciled opening bank/cash balance once. This should be the balance at your chosen go-live date, before recording new transactions.
15. Register two test members before inviting everyone: one full member and one ad hoc member. As owner, approve them under Members, choose their type and discount, and appoint your first committee with permission(s) and a term end date.

## Acceptance check before real records

Use a separate test Firebase project where possible. The built-in demonstration is also safe for trying UI flows.

1. Full member at 20% discount: generate a monthly fee and confirm RM64. Generate again: no duplicate.
2. Ad hoc member: record one attendance and confirm RM15. A repeat must be rejected.
3. Submit a partial payment as the member. Balance must not change until finance verifies it. After verification, balance reduces by the exact amount once.
4. Reject a submission with a reason; it must not change income. Check the bank QR in your banking app and confirm the beneficiary yourself without completing a test payment.
5. Sign in as another member and check they cannot see anyone else's fee details. Check club monthly totals remain available.
6. Test an activity-only committee login and an expired committee login. Neither may access other members' finance records.
7. Record an expense and reconcile the club balance. As owner, reverse a deliberately incorrect test entry and confirm totals and history remain consistent.
8. Check verification email and password reset delivery, mobile layout, printed acknowledgement and CSV export. A real payment should never be required to test the software.

## Normal club routine

- **Beginning of month:** review member status and committee-approved discounts, then Club finances → Fees → Generate monthly fees. The app does not silently back-bill previous months or run an unattended monthly job.
- **Before each session:** add/confirm the date, Malaysia time, venue and court numbers. RSVP is an expression of interest, not a guaranteed reservation or an enforced capacity cap. The committee checks the venue booking and confirms places.
- **After each session:** record actual attendance. For ad hoc members, this creates RM15 receivables; money is counted as income only when payment is verified.
- **When paid:** members scan QR with a banking app and report the transfer reference. Finance matches the reference, amount and bank receipt before approving. Check for reused references manually. A transfer covering multiple fees is allocated fee-by-fee with the same reference; do not count the entire transfer on each fee.
- **For purchases/courts:** record costs actually paid. The schedule's estimated cost does not automatically become an expense. Keep supplier receipts separately with the recorded reference.
- **Monthly close:** reconcile the cash balance with bank/cash records, download the monthly CSV and owner JSON backup, review outstanding fees and committee terms.
- **Annual rotation:** owner changes committee permissions and end dates; membership and fee history remain intact.

## Technical notes and limits

- Static HTML/CSS/ES modules; Firebase browser SDK is pinned to 12.1.0 from Google's CDN. The app uses no npm dependencies at runtime. The package file and lockfile are for local tests only. Google Fonts are optional; local font fallbacks work if unavailable.
- `docs/domain.js`: money and role functions; `docs/store.js`: demo and Firebase data operations; `docs/app.js`: UI; `firestore.rules`: server-enforced authorization. Amounts are stored in integer **sen**, not floating-point ringgit.
- Collections: members, charges, payments, submissions, expenses, activities, attendance, rsvps, summaries, audit, settings. A member's private data is queried by authenticated UID. Members only receive their own private records; aggregated summaries omit member identities and payment references.
- Financial operations use Firestore transactions so payment/charge/summary writes commit together. Payment-submission approval uses a stable payment ID to prevent double approval, and transactions re-check outstanding amounts. The role/term checks are enforced in rules, not only by hiding buttons.
- Finance committee accounts are trusted bookkeeping roles: they can record cash transactions, waive fees and maintain summaries. This is not a bank integration or a tamper-proof double-entry ledger. Application activity logs do not make a Firebase-console administrator's actions tamper-proof. Keep regular backups and bank reconciliations.
- Permanent owner status can only be bootstrapped/transferred by the Firebase project administrator, not via self-registration or another member's browser. Protect the Google and GitHub accounts that own the project.
- Settings/QR are readable only by active verified members. No QR placeholder is used. The code rejects SVG uploads; user-supplied text is escaped when rendered, and CSV formula prefixes are neutralised.
- All financial history is loaded for authorised finance users on refresh in this first version. For a 30-member club this is a practical start, but reads grow over time. Monitor Firestore usage; add pagination/date-window queries before histories become large. Refresh is explicit, not a constant polling loop.
- Firestore's documented free quota includes one free database per project, 1 GiB stored, 50,000 reads/day and 20,000 writes/day. This is a quota, not a promise of unlimited free operation. Stay on Spark to avoid usage-based billing and monitor limits.
- No Cloud Functions, payment gateway, automatic bank reconciliation, WhatsApp/SMS reminders, uploaded bank receipts, capacity enforcement, venue booking API, automated tournament brackets or unattended monthly billing. Tournament draws/results are entered as text. These are possible later extensions, not represented as completed integrations.
- There is no historical spreadsheet import or restore button yet. Backups are JSON exports for review/recovery by a developer. Start from a reconciled opening balance; agree a separate migration for old outstanding member fees before entering real balances. Do not regenerate historic fees using current discounts without checking historical rates.
- No proration for joining/leaving mid-month is assumed. Approved discounts apply to the entire next generated monthly charge; ad hoc discounts are not assumed. Confirm any changes to this policy before launch.
- Concurrent changes by others appear on Refresh or after your next action. Committee expiry is enforced immediately by Firestore even if an older UI remains open. Sign out when using a shared computer.

## Developer verification

Node 22 or newer and Java (for the Firestore emulator) are needed only for development checks, not to host the website.

```sh
npm ci
npm test
npm run test:rules
```

The rule tests use a local `demo-santai` Firebase emulator project; they do not touch a live database. Console permission-denied messages during negative tests are expected.
